Requirements: Kravkatalog: Tjänstekatalogen (Experimentell)

Officiell URL: https://fhir.inera.se/ig/tjanstekatalog/Requirements/tk-tjanstekatalog-requirements Version: 0.1.0
Draft per 2026-09-08 Beräkningsbart namn: TKTjanstekatalogRequirements

Formell kravkatalog för tjänstekatalogen. Varje krav spåras till den/de FHIR-artefakt(er) som realiserar det via satisfiedBy. Se requirements.html för en läsbar vy och mappings.html för den omvända vyn (attribut → krav).

Språk: sv

Dessa krav gäller följande aktörer:

  • Synkroniseringstjänst
  • http://electronichealth.se/fhir/NDI/ActorDefinition/organization-endpoint-writer-actor-er
Sök ändpunkter per organisation ("har")SHALL

Servern SKA stödja sökning av Endpoint-resurser via en sökparameter som returnerar samtliga ändpunkter en angiven organisation listar via Organization.endpoint ("har"-relationen), oavsett vilken organisation som tekniskt förvaltar respektive ändpunkt.

Länkar:

  • Uppfylld av: Endpoint: listed-by
Ändpunktens URL i addressSHALL

Ändpunktens URL SKA anges i Endpoint.address.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Stödda interoperabilitetsspecifikationer per ändpunktSHOULD

Servern BÖR, per nyttolast (Endpoint.payload) som ändpunkten tillgängliggör, ange vilken/vilka interoperabilitetsspecifikationer (API-specifikationer) nyttolasten följer.

Länkar:

  • Uppfylld av: Stödd specifikation (payload profile)
Sök ändpunkter efter stödd interoperabilitetsspecifikationSHOULD

Servern BÖR stödja sökning av Endpoint-resurser via en sökparameter (implements) som returnerar samtliga ändpunkter vars nyttolast stödjer en angiven interoperabilitetsspecifikation, som komplement till REQ-SRCH-3:s representation. Tillagt efter jämförelse med en annan implementation av samma problem.

Länkar:

  • Uppfylld av: Endpoint: implements
Ändpunkt.idSHALL

Varje ändpunkt SKA ha ett unikt id.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Ändpunkt.statusSHALL

Ändpunktens status SKA anges.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Ändpunkt.namnSHALL

Ändpunktens namn SKA anges.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Ändpunkt.adressSHALL

Ändpunktens URL SKA anges (se även REQ-SRCH-2).

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Ändpunkt.giltigFrom / giltigTomSHOULD

Ändpunktens giltighetsperiod BÖR anges.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Ändpunkt.säkerhetsmetodSHOULD

Den säkerhetsmetod som skyddar ändpunkten BÖR anges. Kodverket för detta attribut är i detta utkast preliminärt (example-bindning) — se mappings.html.

Länkar:

  • Uppfylld av: Säkerhetsmetod
Ändpunkt.urlTillAuktorisationsserverSHOULD

Om ändpunktens säkerhetsmetod (REQ-END-6) är OAuth 2.0-baserad BÖR URL till auktorisationsserverns token-endpoint anges.

Länkar:

  • Uppfylld av: URL till auktorisationsserver
Ändpunkt.protokollSHALL

Minst ett protokoll som ändpunkten stödjer SKA anges.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Organisation.id / namnSHALL

Varje organisation SKA ha ett unikt id och ett namn.

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization
Organisation.organisationsnummerSHOULD

Organisationens organisationsnummer BÖR anges som identifierare. Identifierarsystemets URI är i detta utkast ett antagande i väntan på bekräftelse mot Ineras auktoritativa OID/URI-register — se aliases.fsh.

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization
Organisation.endpoint ("har")SHALL

En organisation SKA kunna lista de ändpunkter den "har" via Organization.endpoint, sökbart enligt REQ-SRCH-1.

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization, Endpoint: listed-by
Endpoint.managingOrganization ("förvaltar")SHALL

Varje ändpunkt SKA ange sin förvaltande organisation i Endpoint.managingOrganization, sökbar med standardparametern organization.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Organization.identifier som "logisk adress"SHALL

Organization.identifier SKA fungera som den "logiska adress" tjänstesökning slår upp, sökbar med standardparametern identifier. Ingen separat identifierare för "logisk adress" införs — stakeholder-beslut, se mappings.html.

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization, Tjänstekatalogen: sök-API (externt)
Läsning via tjänstekatalogens admin-APISHALL

Synkroniseringstjänsten SKA läsa organisationer och ändpunkter via tjänstekatalogens administrativa API, särskilt vilka ändpunkter en organisation listar (REQ-SRCH-1), som underlag för synkroniseringen mot EHM.

Länkar:

  • Uppfylld av: Synkroniseringstjänst, Tjänstekatalogen: administrativt API
Anropa EHM:s $add-organizationMAY

Synkroniseringstjänsten FÅR, i rollen Organization Endpoint Writer hos EHM, koppla en organisation till en ändpunkt genom att anropa POST [ehm-base]/Endpoint/[ehm-id]/$add-organization med organisationens organisationsnummer enligt EHM:s specifikation. Personnummer/samordningsnummer hör till EHM:s patientindex och kombinerade sökningar däremellan — inte till organisationsidentifiering i detta anrop, se REQ-WRT-5. Se mappningstabellen i mappings.html för hur organization-parametern fylls från tjänstekatalogens data.

Länkar:

  • Uppfylld av: http://electronichealth.se/fhir/NDI/CapabilityStatement/organization-endpoint-writer-capabilities-er, http://electronichealth.se/fhir/NDI/OperationDefinition/AddOrganizationToEndpoint
Anropa EHM:s $remove-organizationMAY

Synkroniseringstjänsten FÅR, analogt med REQ-WRT-2, koppla loss en organisation från en ändpunkt genom att anropa POST [ehm-base]/Endpoint/[ehm-id]/$remove-organization.

Länkar:

  • Uppfylld av: http://electronichealth.se/fhir/NDI/CapabilityStatement/organization-endpoint-writer-capabilities-er, http://electronichealth.se/fhir/NDI/OperationDefinition/RemoveOrganizationFromEndpoint
Korrelation med EHM:s Endpoint-idSHALL

Varje ändpunkt som ska synkroniseras SKA kunna korreleras med EHM:s eget logiska id för samma ändpunkt i deras register, eftersom $add-organization/$remove-organization adresserar ändpunkten via EHM:s id, inte tjänstekatalogens.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint
Format på organisationsidentifierare mot EHMSHALL

Organisationsidentifierare som skickas till EHM:s $add-organization/$remove-organization SKA vara organisationsnummer i det system och format EHM kräver (urn:oid:2.5.4.97, 10 siffror utan bindestreck). Personnummer/samordningsnummer (http://electronichealth.se/identifier/{personnummer|samordningsnummer}) SKA INTE användas för att identifiera en organisation i detta anrop — de hör till EHM:s patientindex och till sökningar som kombinerar tjänstekatalog med patientindex, inte till denna IG:s scope. Se mappningstabellen i mappings.html.

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization
FHIR-version och formatSHALL

Tjänstekatalogens administrativa API SKA använda FHIR R5 (5.0.0) och SKA stödja JSON. EHM:s Organization Endpoint Writer-gränssnitt gör detsamma (bekräftat i deras CapabilityStatement).

Länkar:

  • Uppfylld av: Tjänstekatalogen: administrativt API, http://electronichealth.se/fhir/NDI/CapabilityStatement/organization-endpoint-writer-capabilities-er
Skapa/uppdatera Endpoint hos EHMSHALL

Innan Synkroniseringstjänsten anropar $add-organization/$remove-organization (REQ-WRT-2/3) SKA motsvarande Endpoint finnas hos EHM, konform med EHM:s profil endpoint-er, mappad enligt mappningstabellen i mappings.html. Observera kardinalitetsskillnaden för payload-specifikationer (EHM tillåter en per payload, denna IG flera) och att säkerhetsmetod/auktorisationsserver-URL kräver kodöversättning respektive strukturell ombyggnad, inte bara värdekopiering.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint, http://electronichealth.se/fhir/NDI/StructureDefinition/endpoint-er
Skapa/uppdatera Organization hos EHMSHALL

Innan Synkroniseringstjänsten kopplar en organisation till en ändpunkt hos EHM SKA organisationen finnas hos EHM, konform med EHM:s profil organization-er, mappad enligt mappningstabellen i mappings.html. Observera att EHM:s Organization.type saknar källa i denna IG:s informationsunderlag (öppen fråga, se mappings.html).

Länkar:

  • Uppfylld av: Tjänstekatalogen Organization, http://electronichealth.se/fhir/NDI/StructureDefinition/organization-er
IndexpostSHOULD

Entiteten Indexpost BÖR modelleras för spårbarhet. REST-exponering (läsning/sökning) i det administrativa API:et är avgränsat bort från detta utkast; direkt skapande/uppdatering från klient är inte avsett, då en indexpost förväntas vara en serverhärledd effekt av registrering av Organisation eller Vård- och omsorgstagare.

Länkar:

  • Uppfylld av: Indexpost (logisk modell)
Vård- och omsorgstagareSHOULD

Entiteten Vård- och omsorgstagare BÖR modelleras för spårbarhet i förhållande till Indexpost.avser. Personuppgifter om vård- och omsorgstagare omfattas inte av detta administrativa API för tjänstekatalogen (teknisk ändpunktskatalog) — se "Avvikelser och tillägg" i mappings.html.

Länkar:

  • Uppfylld av: Vård- och omsorgstagare (logisk modell)
API (Ändpunkt tillgängliggör API, API följer API-specifikation)SHALL

Kopplingen mellan en ändpunkt och de API:er den tillgängliggör, samt vilken/vilka API-specifikationer respektive API följer, SKA kunna uttryckas. Detta realiseras på två komplementära sätt (uppdaterat, se "Avvikelser och tillägg" i mappings.html): dels Endpoint.payload tillsammans med extensionen tk-endpoint-payload-profile (snabb, enhops sökbarhet, se REQ-SRCH-3/4), dels en egen resurs, TKAPIInstance (CapabilityStatement kind=instance), som ger "API" en egen identitet — se REQ-MDL-6/7 för vad den tillför utöver payload-extensionen.

Länkar:

  • Uppfylld av: Tjänstekatalogen Endpoint, Stödd specifikation (payload profile), Tjänstekatalogen API-instans
API-specifikationSHALL

Entiteten API-specifikation SKA kunna registreras och sökas som en egen resurs. Realiseras som TKAPISpecificationCapability (CapabilityStatement kind=requirements), sökbar på kanonisk url — inte ActorDefinition (EHM:s val för sin motsvarande "API Specification"-profil, vilket denna IG avvisar eftersom ActorDefinition är avsett för aktörer, inte specifikationer), inte heller Basic eller ImplementationGuide (denna IG:s tidigare rekommendation, ersatt efter jämförelse med en annan implementation av samma problem — CapabilityStatement.kind=requirements är native FHIR-mekanik för en formell kravbild, och används redan av denna IG:s egna TKAdminAPI/TKSearchAPI). Se "Avvikelser och tillägg" i mappings.html.

Länkar:

  • Uppfylld av: Tjänstekatalogen API-specifikation
Spårbarhet: skapad/senast uppdaterad avSHALL

Vem som skapade eller senast uppdaterade en post SKA vara spårbart. Tidigare avgränsat bort och uppskjutet till en framtida version (löst med serverloggning och/eller Provenance) — nu realiserat via en obligatorisk Provenance-post per registrering, se REQ-TRC-1/2.

Länkar:

  • Uppfylld av: Tjänstekatalogen Provenance
API-instansens egen giltighetsperiodSHOULD

En API-instans (TKAPIInstance) BÖR kunna ange sin egen giltighetsperiod (giltigFrom/giltigTom), oberoende av den tillgängliggörande ändpunktens Endpoint.period. Löser den begränsning som tidigare dokumenterades i mappings.html ("API:ets egen giltigFrom/giltigTom bärs inte separat") — basresursen CapabilityStatement saknar ett eget giltighetsperiod-element, löst med en extension.

Länkar:

  • Uppfylld av: API-instansens giltighetsperiod
API-instansens koppling till Ändpunkt och API-specifikationSHALL

Varje TKAPIInstance SKA referera den ändpunkt som tillgängliggör den ("tillgängliggör", via extensionen tk-api-instance-endpoint) och SKA referera den/de API-specifikationer den följer ("följer", via CapabilityStatement.instantiates), sökbart via en egen sökparameter (instantiates, eftersom ingen standard-sökparameter finns för detta element).

Länkar:

  • Uppfylld av: Tjänstekatalogen API-instans, Tillgängliggörande ändpunkt, CapabilityStatement: instantiates
Provenance krävs vid registreringSHALL

Varje transaction-Bundle som registrerar (skapar/uppdaterar) en Organization, Endpoint eller CapabilityStatement (API-specifikation/API-instans) SKA innehålla minst en Provenance-post (profilerad som TKProvenance) som via Provenance.target pekar ut den/de registrerade resurserna.

Länkar:

  • Uppfylld av: Tjänstekatalogen Provenance
Registrering via transaction-BundleSHALL

Tjänstekatalogens administrativa API SKA stödja systeminteraktionen transaction (en Bundle av typen transaction), så att en registrerad resurs och dess Provenance-post skapas/uppdateras atomiskt tillsammans.

Länkar:

  • Uppfylld av: Tjänstekatalogen: administrativt API
Sök-API exponeras externt via gatewaySHALL

Läsande sökning (read/search-type på Organization/Endpoint) SKA exponeras externt, via en gateway, för sökande konsumenter.

Länkar:

  • Uppfylld av: Tjänstekatalogen: sök-API (externt)
Administrativa API:er endast internaSHALL

Skrivande interaktioner (create/update på Organization/Endpoint/PractitionerRole) SKA vara internt exponerade endast och SKA INTE nås via den externa gatewayen.

Länkar:

  • Uppfylld av: Tjänstekatalogen: administrativt API
Administratörsbehörighetens nivåSHALL

Varje administratörsbehörighet SKA ange en administrationsnivå (local-admin eller central-admin).

Länkar:

  • Uppfylld av: Tjänstekatalogen administratörsbehörighet
Representerad organisationSHALL

En local-admin-behörighet SKA ange vilken organisation den representerar (TKAdministratorRole.organization), analogt med Endpoint.managingOrganization. En central-admin-behörighet representerar samtliga organisationer och utelämnar medvetet detta element.

Länkar:

  • Uppfylld av: Tjänstekatalogen administratörsbehörighet
Behörighetens innehavareSHOULD

En administratörsbehörighet BÖR ange vilket konto/system som innehar den.

Länkar:

  • Uppfylld av: Tjänstekatalogen administratörsbehörighet
Prenumeration på förändringar (topic-baserad Subscription)SHOULD

Servern BÖR stödja R5 topic-baserad Subscription mot ämnet tk-organization-endpoint-changes, så att lokala kataloger kan prenumerera på skapande/uppdatering/borttagning av Organization/Endpoint, som ett alternativ till periodisk pollning.

Länkar:

  • Uppfylld av: Ändringar i Organisation/Ändpunkt
Grundladdning via _lastUpdatedSHOULD

Servern BÖR stödja grundladdning och återsynk genom att sökningarna på Organization/Endpoint kan avgränsas med det generella FHIR-sökparametern _lastUpdated (tidsintervall), utan att en separat grundladdnings-operation behöver definieras.

Länkar:

  • Uppfylld av: Tjänstekatalogen: administrativt API
Undvik rundgång — öppen frågaMAY

I en dubbelriktad federerad miljö FÅR ett ursprungsmärke på Organization/Endpoint användas för att undvika att en lokal katalogs egna uppdateringar studsar tillbaka via prenumerationen. Inte löst i detta utkast — se öppen fråga i mappings.html.
